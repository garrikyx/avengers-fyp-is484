# Telemetry System Log Specifications & Universal Standards

## 1. Executive Summary

This specification defines the two synthetic log streams generated by the `simulator` application: `Fix.log` and `Application.log`. Application records may originate from the main application, a client session, or a venue session; all three variants are written to the same `Application.log` file. Raw log payloads are generated strictly for real-time telemetry extraction and must not be persisted permanently.

---

## 2. Telemetry Stream Specifications

### A. Financial Information eXchange Stream (`Fix.log`)

* **Protocol Standard:** FIX Protocol Version 4.2 (Pipe-delimited `Tag=Value` syntax).
* **Sample Record:**
```text
2026-08-26 11:05:16.123 : 8=FIX.4.2|9=140|35=8|49=MAGIC|56=CLIENT|11=ORD1001|55=AAPL|54=1|38=100|44=150.50|10=112|

```


* **Protocol Field Mapping:**
* `8=FIX.4.2`: Protocol version identifier.
* `9=140`: Body length in bytes.
* `35=8`: Execution Report (order status update / trade fill).
* `49=MAGIC` / `56=CLIENT`: Sender and Target CompID headers.
* `11=ORD1001`: Client Order ID (unique order tracking key).
* `55=AAPL` / `54=1` / `38=100` / `44=150.50`: Symbol, Side (`1` = Buy), Order Quantity, and Price.
* `10=112`: Mandatory 3-digit trailing checksum.

The current generator uses fixed `9` and `10` placeholders and emits only
Execution Report-shaped FIX records. The default agent parser accepts these
synthetic records with checksum validation disabled; strict FIX validation and
complete order/session lifecycles require a richer FIX simulator.


### B. Enterprise Infrastructure Stream (`Application.log`)

* **Format Standard:** Sponsor-provided Magic application log format.
* **Main application record:**
```text
07:51:15.000114 <413013> [N] MAIN: Heartbeat active. Connected session count: 12
```

* **Client record:**
```text
07:51:15.000114 <413013> [I] CS_123: Client session 123 connected
```

* **Venue records:**
```text
07:51:15.000114 <413013> [N] VS_788: VS <BSE|788@BSE|status Connecting|in/out seq 0/0 changed VenueSessionStatus[21169]=Closed/'x' to Connecting/'c'
07:51:45.000090 <413020> [E] VS_788: VS <BSE|788@BSE|status Connecting|in/out seq 0/0 timed out after 00:00:30
07:51:46.690388 <413013> [W] VS_788: VS <BSE|788@BSE|status Closed|in/out seq 0/0 failed to complete connection
07:52:15.027292 <413010> [F] VS_788: GR connection disconnected
```

* **Structure Breakdown:**
* **Timestamp:** Time of day with microseconds (`HH:MM:SS.ffffff`).
* **Thread ID:** Numeric identifier enclosed in angle brackets (`<413013>`).
* **Log Level:** Magic severity code (`[N]`, `[W]`, `[E]`, `[I]`, or `[F]`).
* **Component:** `MAIN`, `CS_<id>` (client), or `VS_<id>` (venue).
* **Payload:** Free-form application system event telemetry.

The main and client component conventions above are synthetic examples; the
sponsor supplied venue examples. The simulator mixes `N`, `I`, `W`, `E`, and
`F` records, including the two signatures configured in `config/agent.yaml`:

```text
07:51:15.000114 <413013> [F] MAIN: java.lang.OutOfMemoryError: heap allocation failed
07:51:15.000114 <413013> [E] MAIN: connection lost to primary db; reconnect scheduled
```

These match `out_of_memory` and `db_connection_lost` respectively. UBS-122's
`AppOutOfMemory` and `AppDbConnectionLost` rules count each signature separately.
Any successfully parsed application record contributes to `app_log_lines` and
keeps `NoLogActivity` quiet; `E`/`F` records also increment `app_log_errors`.
Venue timeout, connection failure, and disconnect messages match the additional
configured signatures, without incrementing the memory or database signature.

To inspect the counters locally, run the simulator and backend, then
`uv run python scripts/health_monitor_demo.py`. The demo reads the same parser
patterns and signatures as `telemetry-agent` and prints totals and per-signature
counts every publish interval. Run `uv run telemetry-agent --config config/agent.yaml`
for the full pipeline with signature-rule evaluation and alert delivery.

The full agent currently publishes alerts and heartbeats. It does not yet
enqueue metric snapshots, so app-log counters can be inspected locally in the
demo but are not automatically published to backend metrics.

## 3. Generation and Rotation Behavior

By default the simulator writes one line every 0.2 seconds, choosing between
the two log files randomly. For application lines it randomly selects main,
client, or venue, then selects an event for that component. The events are
independent synthetic examples; they do not model an ordered connection lifecycle.

Each active log rotates once its size reaches 5 KiB, checked before the next
write. Five numbered archives are retained per file (`.1` is the newest).
Archives remain the same two log types.

Both the simulator and agent resolve `./logs` against their working directory;
run them from the repository root so they use the same files. The full agent
checks rules every 10 seconds, after its 60-second startup grace. Signature
rules enter pending on one evaluation and notify on a subsequent evaluation;
generating an error does not guarantee an immediate alert.

Venue signatures are counted but have no default signature alert rules.
Only `out_of_memory` and `db_connection_lost` have shipped signature rules.
